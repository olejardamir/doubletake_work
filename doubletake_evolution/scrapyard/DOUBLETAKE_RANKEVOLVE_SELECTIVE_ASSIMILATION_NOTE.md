## Mechanisms worth testing, without importing a parallel system

1. **Executable Operating Protocol (EOP):** compile versioned phases, gates, branches, retries, budgets, dependencies, stop rules, required tools and evidence into a runtime-enforced execution graph. The coding model performs bounded node work; it does not self-grant gate passage or rely on remembering a long prompt. **DT seam to inspect:** existing mission intake/scheduler/governance; avoid a second controller. Test process fidelity, deterministic resume and fail-closed invalid transitions against the current mission-prompt-only baseline.
2. **Canonical coding-product node:** adapt existing provider/orchestration interface for Codex, OpenCode, Claude Code and future products, without hardcoding any vendor. Inputs: task, repo snapshot, permissions/tools, budget and context; outputs: patch/artifacts, trace, cost, terminal/failure status. No new parallel registry.
3. **Bounded heterogeneous review/repair:** `propose → independent review → repair → re-review → accept/refuse`, using genuinely different error profiles only when matched-budget rescue outweighs reviewer-introduced defects and cost. A second agent is not inherently beneficial.
4. **Learn product complementarity:** measure conditional error overlap, task/repo context, marginal rescue, reviewer harm, latency and cost. Prefer measured specialization over a fixed A→B review policy; allow single-agent execution when cheaper or equally reliable.
5. **Independent execution-accuracy benchmark:** freeze real defect tasks, repo snapshots, allowed tools, oracles and matched budgets. Compare single product, DT-governed single, heterogeneous repair and multi-agent composition. Include leakage, disconnected gradients, silent miswiring, invalid tests, evaluator tampering and no-op repairs as negatives; report per-condition oracle false-pass risk.
6. **Negative evidence and knowledge reconciliation:** retain failed repairs, rejected changes, product-specific failure patterns, stale/contradictory lessons and provenance within **existing** DT knowledge stores. Prefer newer independent evidence, but do not erase contradictory historical evidence or infer transfer from one environment.

## Original study evidence and limitations

The paper reports **45.8% → 62.5%** all-oracle execution accuracy for budget-matched heterogeneous coding-product composition on its HSTU benchmark (paired +16.7 points, 95% CI [6.6, 26.7]), **10.4%** silent critical-defect rate, and +12.5 points (CI [3.0, 22.0]) on a LitGPT transfer split. These are **author-reported**, not reproduced here. Its deployed model-quality gains involved a human operator at gates; they do not establish full autonomous recovery. Hidden oracles can miss silent faults; an independent evaluator and a comparable budget are mandatory. Knowledge-layer marginal value was not isolated by an on/off ablation. Two ML/PyTorch codebases do not prove general DT transfer. Provider-side compute is not necessarily matched.
