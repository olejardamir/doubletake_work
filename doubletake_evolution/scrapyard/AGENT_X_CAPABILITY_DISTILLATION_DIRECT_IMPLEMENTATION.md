## Unique mechanism and boundary

Harvest is a source of **discovery evidence**, not authority to invent a module, filename, handler, metric or implementation ticket. A distinct, real runtime **Capability Distillation** stage would decompose and validate harvested material before **Assimilation** compares it with current architecture; only a governed, owner-resolved, measurable decision may authorize implementation. Required conceptual sequence:

`source → Harvest record → decompose/clean/normalize/classify → Gate A → Assimilation with real repository/callers → Gate B → bounded experiment or authorized design/code → independent behavioral verification`.

This is not satisfied by adding a `CapabilityDistiller` class, schema, prompt, database status or UI wrapper while any raw-Harvest-to-code bypass remains. Harvest producers (Balancer, Gap-Filling, Frontier, papers, patents, repository/MCP/embedding research) share the same non-authoritative evidence contract. Harvest output should preserve discovery, source, observed mechanism, claimed benefit, context, constraints, confidence and unknowns; generated symbol/path/handler fields, if retained for compatibility, are `UNTRUSTED_SUGGESTION`.

## Atomic distillation operations and decisions

1. **Decompose 0..N** independent technical ideas from a single noisy record. Example: `Query-aware re-rank × Undo/redo ledger` contains two different candidates with different inputs, owners, evidence and tests; zero candidates is legitimate.
2. **Demote contamination**: fictional or promotional framing, generated category/symbol (`cross_modal`, `handle_cross_modal_18`), unexplained score threshold (`accuracy ≥0.8`), unsupported superiority claims, or accidentally joined ideas cannot become requirements. Preserve source trace and reason for discard; do not erase useful mechanisms.
3. **Normalize** each survivor to: problem, mechanism, inputs, outputs, dependencies, constraints, expected behavioral effect, evidence/source IDs, uncertainties and measurable comparison. Distinguish source claim from interpretation.
4. **Classify with operational consequence:** `ALGORITHM`, `ARCHITECTURE`, `POLICY`, `HEURISTIC`, `DATA_TRANSFORMATION`, `MODEL_OR_PROMPT_BEHAVIOR`, `UI_OR_WORKFLOW`, `INTEGRATION`, `OBSERVABILITY`, `TEST_OR_BENCHMARK`, `NON_ACTIONABLE`. A policy or test idea does not default to a Python capability module.
5. **Gate A** technical substance: `PASS | REJECT | DEFER_FOR_EVIDENCE`. Ask what problem, consumer, inputs/outputs, actual mechanism, separable scope, measurable behavior and source evidence exist. Reasons include `NO_TECHNICAL_MECHANISM`, `NO_DEFINED_BEHAVIORAL_DELTA`, `UNSUPPORTED_CLAIM`, `DUPLICATE_TEXT_ONLY`, `ACCIDENTAL_CONCEPT_COMBINATION`, `NON_OPERATIONAL_GOAL`, `INVALID_CLASSIFICATION`, `NO_CONSUMER`, `NO_MEASURABLE_EFFECT`. Rejection leaves an audit trace but no active coding ticket.
6. **Assimilation** checks real existing owners, behavior, overlap, conflicts, callers, reusable code, gap and verification path. Gate A PASS does **not** assert novelty or current-DT deficiency.
7. **Gate B** after architecture comparison: `IMPLEMENT` (proved gap, owner, design, verification), `MERGE` (existing owner needs extension), `EXPERIMENT` (credible but benefit unknown), `NO_CHANGE` (already adequate), `DEFER` (not needed/insufficient prerequisites), `REJECT` (incompatible/harmful). These are **historical design dispositions**, not autonomous permissions in present DT.

**Production coding guard (conceptual, not copy-paste):** Gate A PASS, Gate B IMPLEMENT/MERGE, resolved authorized architectural owner, explicit `BEFORE → AFTER → EXPECTED OBSERVABLE CHANGE → MEASUREMENT`, verification plan and current governance authorization must all hold; all alternate entrypoints must enforce equivalent checks. EXPERIMENT is not IMPLEMENT: require hypothesis, baseline, workload/dataset, metric, bounds, failure criteria and cleanup; only later evidence can support promotion. Fail closed on missing evidence, invalid schema, malformed LLM output, unknown owner, missing delta or missing verification plan.

## Two separable examples and negative controls

**Retrieval reranking (ALGORITHM):** Inputs current objective, retrieved candidates, base scores and optional embeddings. Mechanism could normalize base relevance and combine it with objective cosine similarity using bounded weights; sort by `(-final_score, original_position)` for stable ties. Output reordered top-K and component scores. Measure NDCG@K, MRR, Recall@K and *actual downstream* assimilation acceptance against same-budget baseline. Negative controls: zero focus weight retains base order, absent embedding takes defined fallback, invalid weight is rejected/normalized per contract, stable ties and top-K honored. A handler returning `{"status":"processed","category":"query_reranking"}` is **not** the algorithm. Do not assume the present DT lacks reranking or that this example is beneficial.

**Mutation journal (ARCHITECTURE):** Could preserve authorized rollback/replay evidence but must classify effects as `REVERSIBLE | COMPENSATABLE | SNAPSHOT_RESTORABLE | IRREVERSIBLE | EXTERNAL_SIDE_EFFECT`. Local configuration changes may be reversible; sent mail, remote publication, spent credits or third-party side effects may only be compensatable or irreversible. Need exact transaction/durability boundary, owner authority and side-effect evidence. Without current requirement, Gate B may DEFER. **Never** use this proposal to mutate protected B1 historical state.

**Unsupported metrics:** A harvested `≥0.8` target requires metric definition, labeled corpus, baseline, procedure, sample scope and justified threshold before it becomes an acceptance criterion. No generated threshold is evidence.
