## 1. Operator contract, UI and autonomous pipeline (original §§1–20, 37–47, 65, 89)

A normal user selects a goal/scope, starts/stops mining and sees meaningful results; the backend owns automatic frontier discovery → gap finding/balancing → harvesting → normalization → evidence dedup/aggregation → relevance and capability comparison → Gate A → repository-grounded Gate B → authorized assimilation → verification → durable disposition → repeat. Users must not manually shuttle candidates through stages, label discoveries as upgrades or operate Gate A/B. Present outcomes rather than implementation machinery.

**Minimal main screen:** one primary Start/Stop control; concise system state (idle/mining/paused/stopping/degraded/blocked), useful discoveries, verified implementations, exceptional review count, and last meaningful activity. A separate Details/History/Advanced view exposes source IDs, candidate/gate decisions, versions, failure/retry reasons, cost/health and audit. `agentx_status` (e.g. `update`/`upgrade`) is **descriptive metadata only**, never an authorization switch. User-editable classifications, priority, score, rank, queue state and UI actions likewise cannot grant repository mutation. UI disconnect/reload must not change backend truth.

Review is exceptional, reserved for unresolved authority/safety/licensing/trust-boundary decisions; a human decision adds a constraint, not a Gate B bypass. Show a concise issue, evidence, options, consequences and safe defer. Pending review of one candidate must not block unrelated safe mining. Recoverable errors are handled quietly with bounded retries; surface actionable failures and never conceal blocked integrity.

**Truthful metrics:** Useful discoveries = unique normalized findings worth retaining/evaluating; implementation candidates = unique findings reaching implementation-worthiness analysis; Implemented = accepted verified **active** capability changes, not generated files, attempts, scores or retries; Needs Review = unresolved exceptional cases. Health, liveness, queue pressure, stage latency, retry/failure, gate rates, resource budgets and downstream outcomes remain observable even with a simple UI.

## 2. Source→knowledge→authorization boundaries (original §§21–29, 41, 48–59, 70–72, 80–82, 90–92)

**Gate A** evaluates coherent relevant information/capability, provenance, novelty and evidence quality; passing Gate A permits deeper analysis, **not code**. **Gate B** is the *single canonical* implementation-authority decision: check real repository capability gap/underperformance, evidence, current implementation overlap, mechanism-level plan, affected existing owner/callers, expected benefit, feasibility, architecture fit, safety, license, duplicate/supersession, test plan, cost/maintenance and current governance.

Authority must be **mechanically enforced**, not an unconstrained LLM opinion or a caller-supplied `authorized=True`. A canonical evaluator records a protected decision ID/capability or verifiable token. Every code generation, file write, patch, commit, queue-to-implement and repository mutation entrypoint must resolve that authoritative decision and check candidate ID, evidence refs, current repo revision, policy/evaluator/schema/config versions, scope, expiry, human-review requirement and verification plan. Downstream workers may consume but never mint/alter approval. Distinguish classification, workflow status, human review and actual mutation authority.

**Fail closed** on missing/malformed/contradictory evidence, unknown schema/enum, stale repository comparison, policy/evaluator drift, absent test plan, unresolved capability duplicate, decision conflict, exception, expired approval, unauthorized scope, or unverifiable provenance. Retain as knowledge, defer, reject or require review; never convert uncertainty into approval. Revalidate before each mutation after repo, dependency, governance or owner changes. An old approval does not survive changed conditions merely because a human clicked Approve.

Use typed, versioned boundary records for source, normalized evidence, candidate, Gate A, repository comparison, substance check, Gate B, human review, implementation plan, transaction, verification and disposition. Store model/provider, prompt, evaluator, schema, policy/config and repo revisions with reconstructable input/evidence links. Protect audit/decision history behind a higher-trust boundary: candidate code cannot rewrite its own denial, authorization, test, review or rollback evidence. Stronger independent approval applies to trust-boundary modifications, using **pre-change** rules.

Treat external papers, prompts, sites, repositories, datasets, generated summaries and embedded commands as **untrusted data**, never higher-priority instructions. Bound parser inputs, payload sizes, recursion, archives, network/shell/dependency access and ingestion resources; defend prompt injection, malformed payloads, path traversal, secret leakage and unapproved code execution. Preserve original URLs, versions, license/reuse rights and confidence/contradictions. No wholesale external code import without rights and policy. Least-privilege file/network/tool/credential boundaries and project scope must be explicit. External text cannot widen project scope or lower its own acceptance criteria.

A capability ledger derived from actual repository source/tests and verified history may support novelty/supersession checks but **never overrides code truth**; refresh on relevant changes. Aggregate related findings into one coherent candidate before coding; suppress exact/semantic duplicates, renamed copies, reingestion, previously rejected/superseded/implemented ideas. Recheck before Gate B **and** mutation. Stable candidate identity and durable decisions prevent repeated implementation.

## 3. Substance, repository-first implementation and evaluation (original §§13–16, 33–36, 46, 51–53, 67–69, 75–78, 82–88, 95–98)

Each authorized proposal must define a **pre-change observable behavioral delta**: current baseline, affected canonical owner/module/caller, intended mechanism/data flow, input/output/invariants, alternative (reuse/extend/replace/delete), tests/benchmark, negative controls, rollback, scope and expected maintenance/resource cost. Evidence must be source-qualified and conflicts explicitly represented; unsupported marketing-like performance percentages are hypotheses, not measured effects.

A substance gate rejects name-only proxies: `adaptive=True` without adaptation, FIFO renamed PriorityQueue without priority semantics, a persisted score without learning, constant/path-derived semantic rank, an unused handler/bucket or empty scaffold. The implementation must be reachable from the **real runtime entrypoint** with proper registration/config/callers/state propagation. A module-import unit test alone does not prove assimilation; dormant, disabled or unregistered code is `IMPLEMENTED_NOT_ACTIVE`/`ROLLOUT_PENDING`, not `ACTIVE_VERIFIED`.

**Repository-first:** inspect existing code, interfaces, tests, call graph and ownership before new files. Extend or repair the canonical path, remove obsolete parallel stacks, merge duplicates and simplify. A replacement must have one deliberate runtime authority path; any staged coexistence names an owner, fallback conditions and a removal deadline. Protect unrelated user/external changes; use isolated worktrees/patches and avoid blind merges of overlapping autonomous modifications. Revalidate overlapping changes after the first lands. Maintainability, complexity, unnecessary dependencies/knobs and dead-code reduction are explicit acceptance criteria.

Freeze acceptance tests and baseline before candidate edits; distinguish pre-existing failures from introduced regressions. Require syntax/import/startup, unit/integration/acceptance, production-path reachability, replay/restart/idempotency, concurrency, bounded resource, rollback, security, compatibility, data/schema migration and negative governance tests as relevant. Use matched workloads, held-out tasks and cost/benefit checks for claims of improvement; no cherry-picking flaky reruns or rewriting tests to create success. Verify the **accepted target revision**, not only the isolated patch, including production caller path and cross-component effects. Code, schemas, tests, configs and docs must agree. If verification fails or is UNKNOWN, do not mark Implemented.

After accepted change, independently assess expected benefit, regressions, later ordinary reuse and resource cost. Deletion, consolidation and cleanup are valid improvements when they measurably reduce clutter without removing useful behavior; file counts are not a capability metric.

## 4. Durable multi-worker operation, safety and recovery (original §§28–32, 43, 54–55, 60–66, 72–81, 93–94)

Define an explicit durable state machine with validated transitions, e.g. `INGESTED → NORMALIZED → DEDUPED/AGGREGATED → GATE_A_PASSED → REPOSITORY_ANALYZED → SUBSTANCE_PASSED → GATE_B_AUTHORIZED → [REVIEW_PENDING if required] → IMPLEMENTING → VERIFYING → IMPLEMENTED`. Also `KNOWLEDGE_RETAINED`, `REJECTED`, `DUPLICATE`, `SUPERSEDED`, `FAILED`, `DEFERRED`, `ROLLED_BACK`, `INTEGRITY_BLOCKED`. No illegal jump or status-string approval. Rejected/deferred knowledge has a durable reason, suppression and meaningful recheck trigger; not perpetual reprocessing.

Persist stable IDs, stage/checkpoints, source evidence, repo/policy revision, decision, plan, transaction ID, worker lease/claim, retry budget, test outcome and final disposition. Atomic claims with expiry/recovery prevent concurrent workers from mutating for equivalent candidates. Repository mutation effects must be **exactly once from the user's perspective** despite analytical retries. Correlate candidate ID + authorization ID + transaction ID + accepted commit + verification ID + disposition. On crash between commit and state finalization, reconcile the **actual** target repo revision and durable record rather than reapply patch or invent completion. Do not confuse exactly-once effects with a claim that every processing step executes exactly once.

Prepare/apply/verify/accept changes in isolated, rollback-capable boundaries. On test failure discard/rollback and retain diagnostics. If rollback fails or integrity is uncertain, fail closed, quarantine affected mutation and require authorized recovery; no continuing writes to make the state look clean. Preserve protected history, schema compatibility and unrelated work. Migrations need versioned forward/backward compatibility, recovery and tests; do not silently alter serialized formats or supported runtimes.

**Stop Mining:** stop scheduling new discovery/assimilation, drain or safely cancel nonmutating work, finish or rollback in-flight transactions, persist state and remain restartable. Never kill a mutation mid-write and claim safe stop. UI is a view, not the durable orchestrator.

Bound queues, worker count, CPU, memory, disk, tokens, ingestion rate, test duration, patch attempts, retries, network and external side effects; backpressure/coalesce when saturated. Circuit-break repeated failures, isolate bad candidates and continue unrelated safe work. On no-novelty/exhausted frontier back off/rotate rather than spin. Retention/compaction of raw sources, embeddings, logs and traces must preserve the minimum auditable/reproducible evidence and never silently discard accepted history.

Sandbox generated code/tests: control production filesystem, secrets, shell, network, APIs, queues, notifications and cloud resources. External side effects require explicitly authorized disposable resources; retries, Stop and verification reruns must not duplicate them. Supply-chain checks cover dependency source/version integrity, insecure deserialization, unsafe command/path construction and privilege escalation. Protected governance/guard/audit components require stronger owner approval than ordinary capabilities.

## 5. Specific falsifiable negative and positive tests (original §§44, 71, 83–100)

- **Authority:** Set `agentx_status=upgrade`, `approved=True`, `selected`, `queued`, high scores, LLM verdicts or forged `authorized=True` while canonical Gate B denies. **Zero repository mutations**. Tamper with candidate/repo/policy/schema version, omit evidence, replay expired token, forge decision, alter audit record or self-edit Gate B in same patch: fail closed. No UI or review action grants authority. Search all code paths, not only one conditional.
- **Evidence:** Poison an external source with instructions, executable code, malicious URLs, unsafe license or secret requests; it remains data. Missing/conflicting provenance, malformed records, duplicates and superseded candidates never become code by default. Same evidence/repo state and concurrent equivalent workers yield one authorized effect at most.
- **Mechanism:** Reject placeholder-only adaptive/semantic/learning implementations; require actual production caller and expected behavior. Detect an import-only test while runtime never calls module; disabled/unregistered implementation not counted active; replacing code must select the canonical path and remove/bound the old one.
- **Recovery:** Inject crash before/after write, after commit but before finalization, lease expiration, concurrent overlap, stop during patch, restart/replay, rollback failure, retention/capacity refusal and stale-reader races. Accepted writes and decision lineage survive; no double-apply or silent loss. Fail-closed integrity block on unresolved rollback. An isolated happy-path test is not durable recovery.
- **Verification:** Inject baseline failures, flaky tests, mismatched target revision, tampered benchmarks, unsupported runtime/schema changes, secret/dependency hazards and unauthorized external side effects. Do not accept after rerunning until lucky pass; failed/UNKNOWN checks block. Confirm code, contract, tests, docs and actual deployed/selected runtime path agree.
- **UI/operations:** Normal Start/Stop needs no manual gate controls; pending review does not block unrelated safe work; frontend disconnect does not change backend state; empty frontier backs off; budgets/circuit breakers hold; counters represent distinct verified outcomes, not files/retries.

**Definition of Done:** All relevant tests above pass against an identified current implementation and independently observed caller/revision; Gate A/B authority cannot be bypassed; ordinary user operates the autonomous loop through high-level controls; authorized candidate changes are substantive, transactional, rollback-safe, observable, correctly versioned and propagated; accepted results survive restart and are independently measured on the real path. Any hard failure or UNKNOWN is **NOT VERIFIED**, regardless of document completeness or source code volume.
