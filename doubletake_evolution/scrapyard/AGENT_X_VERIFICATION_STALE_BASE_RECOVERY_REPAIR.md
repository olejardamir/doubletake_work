## Atomic mechanism and authority boundary

1. **Compute three orthogonal projections first:** accepted/current semantic revision, production implementation/source revision, and verification/test/proof revision. Do not classify verification drift by an early return. Expose accepted/current verification digest and exact changed verification paths only when immutable baseline snapshots permit; legacy aggregate-only v1 baselines must report unknown paths rather than fabricate diffs. Git HEAD alone is not the accepted verification snapshot.
2. **Classification matrix (verification drift does not mask production truth):**
   - semantic same + implementation same + verification same → `SYNCED`.
   - semantic same + implementation same + verification changed → evidence-only refresh-needed state (existing `EVIDENCE_GATHERED` only if semantically appropriate), **not** `SYNCED` or unrecoverable `STALE_BASE`.
   - implementation changed + semantic same, regardless of verification → `IMPLEMENTATION_AHEAD` with conflict.
   - semantic changed + implementation same, regardless of verification → `SEMANTIC_AHEAD` with conflict.
   - both semantic and implementation changed, regardless of verification → `BOTH_DIVERGED` with conflict.
   - corrupt baseline, evidence, model digest or repo identity → fail closed; no auto-legitimization.
3. **Verification-only refresh is a new governed *evidence* transaction, never a production write grant.** Only when semantic and implementation revisions exactly match the accepted base: inspect verification diff; execute required deterministic tests; confirm accepted invariants and coverage have not been weakened/deleted; issue a *new paired* immutable target + verification artifact bound to unchanged semantic and implementation revisions, current verification revision, repo identity, run/change ID and actual current source snapshot; consume evidence once; atomically promote through the existing canonical baseline builder; independently reassess `SYNCED` twice without intervening changes. No old target paired with unrelated new proof, no direct `semantic_code_sync.json` edit, no blindly copying digest, no accepting mere green tests after deletion of critical assertions. Material verification-contract changes require governed review.
4. **Mixed drift follows existing governed conflict resolution:** persist a real `SyncConflict` for recoverable `IMPLEMENTATION_AHEAD`, `SEMANTIC_AHEAD`, `BOTH_DIVERGED` and partial implementation states. Bind conflict identity and `validate_resolution_transaction()` to accepted/current semantic, implementation and verification revisions, affected paths and repo identity. If verification changes again, reject stale conflict/evidence replay. Verification-only refresh must never run first on mixed drift.
5. **Failure/restart/concurrency:** On failed tests, missing evidence, weakened requirements, corrupt authority or stale replay, keep old accepted baseline untouched, deny mutation and return precise `VERIFICATION_REFRESH_FAILED`/policy diagnostics. At every crash boundary (pre-refresh, target issued, proof issued, pre-promotion, post-consumption, post-promotion/pre-reassessment), recover either old accepted state or fully coherent new state—never half-updated or double-consumed evidence. Two simultaneous refreshers: one atomic winner; loser reloads winner, reassesses and reuses without consuming duplicate evidence. Runtime evidence, run-local artifacts, conflicts and issued baselines must **not** feed recursively into `verification_snapshot()` and cause self-refresh churn.
6. **UI and bootstrap:** If verification-only drift is safely recoverable, checkpoint refreshes it before continuing the *same pending build request* through ordinary semantic-first authorization. If refresh fails, return an accurate nonretryable verification-policy result; provider-dependent transient assessment may be retryable. Do not turn every mismatch into a generic 403. Historical source suggested trusted external/bootstrap maintenance when the ordinary gate itself is deadlocked; this is **not** a standing bypass, self-grant or authorization to change protected DT history. Normal write scope must remain governed.
