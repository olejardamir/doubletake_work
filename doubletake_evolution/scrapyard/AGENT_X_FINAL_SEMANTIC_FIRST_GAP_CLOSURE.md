## Four distinct claimed defects and intended contract

1. **Explicit external request-source read vs project mutation authority.** Historical `semantic_first/materialize.py` used `workspace_root` as both boundaries, rejecting an explicitly referenced specification outside the repository. A user-selected absolute regular-file source can be read *only* under explicit read-only source policy; this never authorizes writing outside the project. Resolve symlinks and reject missing paths, directories, devices/sockets, oversized/unsupported files, disallowed targets, globs, recursive crawling, implicit `$HOME`/environment reads. Preserve absolute source identity internally (e.g. `external-file:<digest>`), digest and provenance; do not forge repository-relative paths. Reject external source in mutation/write/delete/overlay scopes unless an independent explicit edit authorization exists.
2. **Materialize before semantic interpretation.** Historical `design_target_state` materialized *after* `interpret`, so the model saw only a path rather than specification content. Required order: raw request → explicit source materialization → governed semantic request context → interpretation → target design. One `MaterializedRequest(original_text, sources, augmented_text, source_digest)` identity/digest must feed interpretation, design, scope, overlay and freshness checks; source content remains untrusted data, never system/developer authority. Before first mutation, rehash/re-read and compare bound digest; on change revoke stale authorization and repeat materialization/interpretation/design/scope seal. Avoid normal double materialization.
3. **Exact semantic target determines write scope.** Historical `write_scope.py` treated `affected_capability` as permission to write all `Capability.module_paths` and `ImplementationBinding.module_paths`. Impact is evidence, not write authority. Per component require `implementation_action = none | modify_existing | replace_existing | remove_existing | create_new`, `implementation_targets` and `proposed_new_paths`; derive writes only from accepted semantic target + action + canonical binding, not broad affected capability. Canonical target namespace `binding:`, `module:`, `interface:`, `identity:`, `responsibility:` (or uniquely resolved plain ID); ambiguity fails `UNRESOLVED_WRITE_SCOPE`. `none` grants zero paths; modification selects exact binding; replacement includes only justified incumbent, replacement, caller/registration/config/migration/test effects; deletion exact obsolete target; new paths are repository-relative, non-escaping, non-colliding and owner-bound. Capability fallback only when **exactly one** relevant implementation path is provable. Read/verification scopes may be broader than mutation. A single bounded governed scope-repair may return validated canonical target IDs, **not** arbitrary writable paths; failed/ambiguous repair stops without a second loop or write. Every writable path records action, target component, binding and derivation. Coherence with accepted `prompt_only`, `prompt_driven`, `deterministic` authority decision is required.
4. **Recompute and independently verify current canonical baseline.** After code and regression tests, regenerate semantic model using canonical tooling (not hand-editing JSON); include source materialization, trust/freshness, exact target binding, scope separation and bounded repair. Compute actual production `source_snapshot`, implementation, verification and semantic/model revisions; issue **fresh** paired target/verification evidence bound to those revisions; validate/consume atomically and persist canonical `semantic_code_sync.json`. Do not hand-copy hashes, reuse consumed evidence or reuse historical September 13 baseline. Source snapshot includes runtime-authoritative materializer, scope, pipeline, interceptor/provider/governance changes; distinguish tests as verification evidence. Verify exact revision equality, independently assess `SYNCED`, repeat unchanged `SYNCED` immediately, restart and reassess. Stored `SYNCED` text alone proves nothing; refuse stale base, ahead/drift, conflict, missing evidence, wrong repository identity, and junk transaction state.
