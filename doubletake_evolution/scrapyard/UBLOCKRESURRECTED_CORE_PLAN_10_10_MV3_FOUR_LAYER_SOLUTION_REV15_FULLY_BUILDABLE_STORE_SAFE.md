# uBlockResurrected Core Engine Plan — Rev15 Fully Buildable Store-Safe Current-Chrome MV3 Build Specification

## Document status

**Previous version reviewed:** Rev13 Corrected Current-Chrome MV3 Build Specification.

**Rev13 rating:** 9.7/10.

Rev13 was close, but not fully 10/10 because several implementation details still needed tightening: the sample `getMatchedRules()` code incorrectly treated matched-rule records as if they contained `requestId`; the response field name was wrong; attribution needed to be framed as tab/time-window evidence, not exact request-level tracing in packed Chrome; static capacity needed a clearer guaranteed-vs-opportunistic policy; source-map keys needed to stay `rulesetId:ruleId`; the roadmap still contained a stale globally-unique-rule-ID claim; and packed-extension validation needed a stricter rule that invalid static rules must fail release because Chrome may ignore them in packed builds.

Rev14 corrects those points. The goal remains ambitious: build the strongest MV3-native blocker on the declared corpus. The method is now stricter:

```text
build only what stable Chrome MV3 can do today
use DNR correctly and aggressively
use safe dynamic rules for user-authored network rules
use local editor/import/export for custom rules
optionally allow explicit user-reviewed URL import, never automatic rule fetching
use getMatchedRules + source maps for attribution
mark unsupported syntax honestly
ship a smaller, testable module set
prove superiority with a pinned certificate
```

This revision intentionally removes features that were useful as long-term ideas but are not available in current Chrome MV3 or would create unnecessary implementation risk for a 1.0 release.

# 1. Scope

Design a de novo Chrome MV3-native content blocker that outperforms the strongest available MV3 blocker on the declared corpus.

The primary runtime target is stable Chrome MV3 using `chrome.declarativeNetRequest` as the network-blocking engine.

The extension must not rely on deprecated blocking `webRequest`, remote executable code, runtime `eval`, or speculative browser APIs for the public Chrome Web Store release profile.

## 1.1 Chrome Web Store compliance commitment

All extension logic must be packaged with the extension. The extension must not load or execute remotely hosted JavaScript, remote scriptlets, remote libraries, or remote logic.

Blocking behavior may be changed only through these paths:

1. **Packaged static rulesets** delivered through an extension update.
2. **Local user-authored rules** typed, pasted, imported from a file, or generated by in-extension UI actions.
3. **Optional explicit user-reviewed URL import**, disabled by default, where the user clicks an import button, reviews the fetched text/diff, and explicitly applies it as local user rules.

The extension must not perform automatic, scheduled, silent, background, website-triggered, or server-pushed rule updates.

## 1.2 Project-name note

The project name may remain `uBlockResurrected` as branding. The specification does not promise API parity with unavailable Chrome APIs. The product target is the best measurable current-Chrome MV3 blocker.

# 2. Current Chrome MV3/DNR facts used by this plan

Rev15 is based on stable Chrome MV3 DNR behavior available today, with version-gated use of features that are only available in newer Chrome versions. It tightens Rev14 by adding static-key `$removeparam` limits, regex runtime checks, optional tabs-API popup handling, user-adjustable `:has()` budgets, stricter URL import controls, domain-condition length limits, concrete performance metrics, and a reproducible benchmark harness requirement.

## 2.1 Ruleset types

| Ruleset type | Update path | Persistence | Main use |
|---|---|---|---|
| Static | Packaged in extension and updated through extension releases. | Extension package lifetime. | Core curated filter lists. |
| Dynamic | Managed by extension JavaScript while running. | Persists across browser sessions and extension upgrades. | Persistent user-authored network rules. |
| Session | Managed by extension JavaScript while running. | Cleared when browser shuts down and on extension update. | Temporary unbreak / temporary site action rules. |

## 2.2 DNR limits and capability probing

The extension must probe or read the actual browser capability profile at startup and extension update.

Expected Chrome 121+ profile:

| Capability | Value / rule |
|---|---|
| Packaged static rulesets | Up to 100 declared rulesets. |
| Enabled static rulesets | Up to 50 enabled at one time. |
| Guaranteed static rule floor | 30,000 enabled static rules guaranteed. |
| Safe dynamic rules | Up to 30,000 dynamic rules in Chrome 121+. |
| Unsafe dynamic rules | 5,000 maximum. |
| Session rules | 5,000 maximum. |
| Unsafe session rules | 5,000 maximum. |
| Regex rules | 1,000 per ruleset type. |
| Compiled regex size | Must be below Chrome’s compiled regex size limit; treat 2 KB as the build-time rejection target. |
| Disabled static rules | Up to 5,000 disabled static rule IDs. |

**Regex rule acceptance policy:**

1. Static regex rules are rejected at build time if estimated compiled size is greater than 2 KB **or** if `isRegexSupported()` returns `false` when available in the target Chrome version.
2. For dynamic/session user rules, the extension must call `isRegexSupported()` before adding any regex rule where the API is available. If unsupported, or if the regex would exceed the per-extension budget, reject the rule with a user-visible error.
3. The total number of user-created regex rules, dynamic plus session combined, is capped at **200** to avoid performance degradation. The extension must warn the user when approaching **150**.

**Static-capacity policy:**

The public release profile must distinguish **guaranteed** capacity from **opportunistic** capacity. The certificate may rely only on the 30,000 guaranteed enabled static-rule floor. Additional static rules may be enabled only when `getAvailableStaticRuleCount()` confirms available capacity at runtime. If additional static capacity later disappears, the extension must fall back to the guaranteed profile without changing the superiority claim.

Safe dynamic actions are:

```text
block
allow
allowAllRequests
upgradeScheme
```

Unsafe/scarce dynamic actions include:

```text
redirect
modifyHeaders
```

## 2.2.1 Version-gated DNR feature policy

The capability profile must not assume that every documented DNR field exists in every supported Chrome build. The release profile must record:

```json
{
  "minimumChromeVersion": "PINNED_MINIMUM",
  "features": {
    "safeDynamic30000": "required-for-1.0",
    "responseHeadersCondition": "optional-chrome-128-plus",
    "topDomains": "optional-chrome-145-plus",
    "urlTransformQueryTransform": "required-only-if-removeparam-enabled"
  }
}
```

Rules that require a field unavailable in the current browser profile must be rejected at compile/import time and listed as `UNSUPPORTED_FOR_BROWSER_PROFILE`, not silently downgraded.

## 2.3 DNR priority semantics

The compiler must assign explicit priorities. It must never depend on overlapping static/dynamic priority ranges or undocumented tie behavior.

| Priority range | Purpose | Gap protection |
|---|---|---|
| 900000–999999 | User emergency override / important-equivalent allow/block. | Static rules never use this range. |
| 820000–839999 | Session rules (temporary). | Static rules never use ≥820000. |
| 800000–819999 | User persistent dynamic rules (safe actions). | Static rules never use this range. |
| 700000–799999 | Reserved for future user-managed ranges. | Static rules never use this range. |
| 600000–699999 | User-disabled static-rule replacement rules. | Static rules never use this range. |
| 500000–599999 | Packaged exceptions / allow rules. | Dynamic rules never use this range. |
| 400000–499999 | Packaged high-confidence block rules. | Dynamic rules never use this range. |
| 300000–399999 | Packaged tracker/privacy rules. | Dynamic rules never use this range. |
| 200000–299999 | Packaged annoyance / nuisance rules. | Dynamic rules never use this range. |
| 100000–199999 | Low-risk upgradeScheme rules. | Dynamic rules never use this range. |
| 1–99999 | Experimental or disabled-by-default packaged shards. | Dynamic rules never use this range. |

**Tie-breaking rule:**
Within one extension, before-request candidates are ordered first by explicit priority. If priorities are equal, Chrome orders actions as `allow` / `allowAllRequests` before `block`, then `upgradeScheme`, then `redirect`. Across extensions, Chrome applies additional ordering, and browser vendors explicitly warn that same-action/same-priority ordering is not stable enough to depend on. Therefore the compiler and dynamic rule manager must use the priority ranges above exclusively and must reject any rule whose assigned priority overlaps a different lane.

# 4. Layer 1 — Packaged static DNR core

## 4.1 Static ruleset strategy

Static rulesets are compiled at build time from curated filter inputs and shipped in the extension package.

V1 static shards:

| Shard | Purpose | Enabled by default |
|---|---|---|
| `core-ads` | High-confidence ad network blocking. | Yes |
| `core-trackers` | High-confidence privacy/tracker blocking. | Yes |
| `core-allow` | Packaged exceptions / unbreak rules. | Yes |
| `annoyances-lite` | Conservative nuisance blocking. | Yes, if within budget. |
| `regional-pack-*` | Optional regional rules. | User selected. |
| `site-pack-*` | Optional high-value site packs. | User selected. |

The static compiler must optimize for correctness first and rule count second.

Required compiler behavior:

- deduplicate equivalent rules;
- merge safe domain conditions;
- avoid regex when `urlFilter` is enough;
- reject overbroad rules unless explicitly whitelisted;
- assign deterministic rule IDs;
- assign deterministic priorities;
- produce source maps;
- assign rule IDs that are unique inside each static ruleset, and also maintain a globally unique `globalRuleKey = rulesetId + ":" + ruleId` in the source map. `updateStaticRules()` is called with an explicit `rulesetId`, so cross-ruleset numeric ID reuse is not itself a collision; the global source-map key prevents diagnostic ambiguity;
- produce unsupported syntax report;
- produce budget report;
- fail CI on invalid DNR output.

# 5. Layer 2 — Safe dynamic user-rule workspace

## 5.1 Core principle

Dynamic DNR is not treated as scarce for safe user rules on Chrome 121+. Persistent user rules should use safe dynamic rules whenever possible.

The user workspace is the main superiority feature:

```text
write/paste rule
validate
preview generated DNR/cosmetic output
show budget impact
apply
undo
export
```

## 5.2 User rule lanes

| Lane | Storage | DNR target | Use |
|---|---|---|---|
| Persistent user network rules | `chrome.storage.local` ledger | Dynamic rules | User-authored block/allow/upgrade rules. |
| Temporary site exceptions | `chrome.storage.session` or local metadata | Session rules | Temporary unbreak, tab/session testing. |
| User cosmetic selectors | `chrome.storage.local` | Content script CSS injection | Locally authored selectors. |
| Disabled static rules | `chrome.storage.local` metadata | `updateStaticRules` | Disable matched static rule by ID. |

**Session rule budget warning and cleanup:**

- Warn when session rule count reaches **4,000**, not 4,500.
- Recommend converting oldest or least-used temporary rules to persistent safe dynamic rules where appropriate.
- Provide a **Clear session rules older than 7 days** button in options.
- Optionally auto-clear session rules on extension restart if the count exceeds 4,500, with a user notification.

## 5.3 Rule lowering planner

The rule lowering planner decides where each user rule goes.

| Input rule | Lowering result |
|---|---|
| Safe network block | Dynamic DNR `block`. |
| Safe network allow | Dynamic DNR `allow` or `allowAllRequests`. |
| HTTP upgrade | Dynamic DNR `upgradeScheme`. |
| Temporary unbreak | Session DNR where possible. |
| Static false positive | Prefer `updateStaticRules` disable by matched static rule ID, then narrow allow rule. |
| Cosmetic selector | Local cosmetic selector store. |
| Arbitrary redirect | Unsupported unless packaged safe redirect is available. |
| Header modification | Only whitelisted safe header operations; otherwise unsupported. |
| Response-body rewrite | Unsupported. |

**Dangerous rule example detection:**
If a user rule would match almost all URLs, for example `*$domain=~bank.com` or `^https?://.*` without resource-type restrictions, the validator must show a prominent warning: **“This rule may break most websites. Apply anyway?”** and require an extra confirmation click.

11. User must explicitly confirm installation.

# 6. Layer 3 — Basic cosmetic engine

## 6.1 V1 cosmetic principle

V1 uses a simple content-script CSS injector, not a complex procedural engine.

Supported in V1:

- packaged static cosmetic selectors;
- user-authored cosmetic selectors from local storage;
- cosmetic exceptions;
- standard CSS selectors;
- cautious use of native CSS `:has()` where supported;
- **scriptlet injection (`##^script:...`) is not supported in V1** and is deferred to V2 with packaged, static scriptlets only;
- per-domain selector lookup;
- CPU and selector count budgets.

Deferred to V2:

- `:has-text()`;
- procedural selector language;
- scriptlet framework;
- mutation-heavy dynamic procedural matching.

## 6.1.1 High-risk site policy (concrete definition)

The high-risk site policy triggers when any of the following occur on a domain:

- Cosmetic selector execution exceeds **100ms cumulative time** within 5 seconds.
- Three or more cosmetic-related performance warnings from `LongTaskObserver`, slow style recalculation telemetry, or equivalent local browser performance signals occur in a 30-second window.
- User manually marks the site as “problematic” via popup.

When triggered:

- Disable all cosmetic filtering for that domain as a temporary session exception.
- Show a non-modal notification: **“Cosmetic filtering disabled on this site due to performance issues. Click to re-enable.”**
- Re-enable is a single click. If performance problems recur, offer a permanent disable option.

## 6.2 Basic injector model

```typescript
async function applyCosmeticFilters() {
  const selectors = await getSelectorsForDomain(location.hostname);
  const safeSelectors = selectors.filter(isSafeSelectorForPageBudget);
  if (safeSelectors.length === 0) return;

  const style = document.createElement('style');
  style.dataset.ubr = 'cosmetic';
  style.textContent = safeSelectors
    .map(selector => `${selector} { display: none !important; }`)
    .join('\n');

  // Inject as early as possible to reduce FOUC.
  const target = document.head || document.documentElement;
  target.appendChild(style);

  // Optional: re-apply after DOM changes, but only inside strict budgets.
  observeDomForNewElements(safeSelectors);
}
```

**FOUC mitigation:**
Injection occurs from a `document_start` content script before `</head>` where possible. A limited `MutationObserver` catches dynamically added elements, with a maximum of 5 mutation batches per second and 100 total selectors re-checked. Heavy mutation sites may still show temporary flickering; the user can disable cosmetic filtering for that domain from the popup.

## 6.3 Cosmetic safety

The cosmetic engine must:

- cap selectors per page;
- cap selector text length;
- reject prohibited selectors;
- apply high-risk site policy;
- disable problematic selectors locally;
- support undo for user selectors;
- avoid DOM mutation storms;
- avoid expensive polling loops;
- limit `:has()` selectors to a **configurable budget**:
  - Default: 5 per domain, 50 total across all domains.
  - Advanced settings page provides a slider: **Maximum `:has()` selectors per domain** with values 0 = disable and 5–50 = allowed cap.
  - Warn the user that higher values may slow browsing.
  - The high-risk site policy still applies regardless of budget.
- measure selector execution time per page; if total exceeds 100ms, disable remaining `:has()` selectors for that page;
- provide a popup toggle: **Disable advanced CSS (`:has`) on this site**.

Required files:

```text
src/core/runtime/cosmetic-engine.ts
src/core/runtime/cosmetic-selector-store.ts
src/core/runtime/cosmetic-budget-guard.ts
src/safety/high-risk-site-policy.ts
```

# 7. Layer 4 — Attribution, diagnostics, and certificate

## 7.1 Use `getMatchedRules` instead of custom matching

The extension must not reimplement the DNR matcher for attribution.

Use:

```text
chrome.declarativeNetRequest.getMatchedRules()
```

Then map the matched rule ID to the source map.

Required file:

```text
src/attribution/getMatchedRuleInfo.ts
```

Reference behavior:

```typescript
export async function getMatchedRuleInfoForTab(tabId: number, sinceMs = 10_000) {
  const minTimeStamp = Date.now() - sinceMs;

  const details = await chrome.declarativeNetRequest.getMatchedRules({
    tabId,
    minTimeStamp
  });

  const sourceMap = await loadSourceMap();
  return details.rulesMatchedInfo.map(info => {
    const key = `${info.rule.rulesetId}:${info.rule.ruleId}`;
    return {
      tabId: info.tabId,
      timeStamp: info.timeStamp,
      ruleId: info.rule.ruleId,
      rulesetId: info.rule.rulesetId,
      source: sourceMap[key] ?? {
        sourceList: 'unknown',
        line: null,
        sourceTextHash: null
      }
    };
  });
}
```

Packed Chrome does not provide exact request details through `getMatchedRules()`. Exact request-level details are available only through `onRuleMatchedDebug`, which is for unpacked/debug builds. Therefore the production attribution UI must say **“Rules recently matched on this tab”**, not **“This exact request was blocked by…”**, unless the extension has separate user-visible request context that can safely correlate by time and tab.

**Store justification note:**
`getMatchedRules()` is available when the extension has `declarativeNetRequestFeedback` permission, or when `activeTab` is granted for the tab specified in the filter. The preferred public-store path is **user-triggered activeTab attribution**: the user clicks “Why was this blocked?”, the extension receives temporary active-tab access, calls `getMatchedRules({ tabId })`, and resolves the rule through the source map. If the build includes `declarativeNetRequestFeedback`, the store listing must explicitly state: **“Uses DNR feedback only to show which rule blocked a request when you click ‘Why was this blocked?’ in the popup.”** No continuous polling or telemetry use is permitted. If neither permission path is available, attribution falls back to “rule ID unknown” without functional loss.

## 7.2 Attribution limits

`getMatchedRules` must be user-action driven. The extension must:

- call `getMatchedRules` only in direct response to a user gesture, such as clicking **Why was this blocked?**;
- rely on user-gesture calls because they are not subject to the 20-calls-per-10-minutes non-user-gesture quota;
- avoid attribution caching, because stale matched-rule evidence can mislead users;
- fetch fresh matched-rule evidence each time the user explicitly asks for it;
- make no background, alarm, timer, polling, or telemetry-based calls to `getMatchedRules`;
- degrade gracefully if `activeTab` or `declarativeNetRequestFeedback` is unavailable;
- never use attribution as the blocking path;
- never claim exact request attribution from `getMatchedRules()` alone in packed Chrome.

## 7.3 Source map requirements

Every compiled static and dynamic rule must have a source-map entry.

```json
{
  "rulesetId": "core-ads",
  "ruleId": 401203,
  "lane": "static-core",
  "sourceList": "easylist-normalized",
  "sourceLine": 15822,
  "sourceTextHash": "sha256:...",
  "generatedBy": "dnr-compiler@epoch"
}
```

## 7.4 Diagnostics privacy

Local diagnostics may show full URLs to the user. Exported bug reports must redact full URLs by default and require explicit user confirmation to include full URLs.

Required files:

```text
src/attribution/getMatchedRuleInfo.ts

src/core/evidence/unsupported-syntax-report.ts
src/diagnostics/sanitized-export.ts
```

## 8.3 Safe redirect subset

DNR redirects are supported only when all of the following are true:

- the redirect uses one of Chrome’s current DNR redirect forms: packaged `extensionPath`, safe URL transform, `regexSubstitution`, or `URLTransform.queryTransform`;
- any packaged redirected resource is declared in `web_accessible_resources`;
- the rule action fits DNR schema and browser-version capability checks;
- the rule falls inside the unsafe dynamic budget if user-authored;
- the redirect does not target remote executable code;
- source map records exact origin;
- `$removeparam` lowers only to constrained `queryTransform` removal/replacement rules, never arbitrary response rewriting;
- all regex rules are checked with `isRegexSupported()` where possible and statically estimated at build time. If estimated compiled size exceeds **2 KB**, the rule is rejected and logged in `unsupported-syntax-report.json`.


**Static-key `$removeparam` lowering:**

- Only parameter names that are plain strings may be lowered: no `~`, no regex, no wildcard, no value predicates.
- Example supported: `$removeparam=fbclid`.
- Example unsupported: `$removeparam=/^utm_/`.
- Example unsupported: `$removeparam=utm_source=/newsletter/`.
- The compiler must reject unsupported `$removeparam` patterns and log them in `unsupported-syntax-report.json`.

## 8.4 Header modification subset

Header modification is supported only for a strict allowlist.

```text
remove/modify Referer only where safe and user-visible
remove/modify Cookie only where safe and user-visible
other headers require explicit implementation approval
security-sensitive response headers are unsupported unless current Chrome DNR safely supports the exact operation
```

---


## 8.5 Domain condition length limits

- The compiler must ensure that, for any generated DNR rule, the serialized domain-related condition payload does not exceed **2048 characters**. This includes `domains`, `excludedDomains`, `initiatorDomains`, `excludedInitiatorDomains`, `requestDomains`, and `excludedRequestDomains` where used by the target Chrome profile.
- If a rule’s domain condition exceeds this limit, the compiler must attempt to split it into multiple DNR rules only when the split preserves semantics.
- If a safe semantic split is impossible, the compiler must drop the rule and record it in `unsupported-syntax-report.json` with reason `DOMAIN_CONDITION_TOO_LONG`.
- User-created dynamic rules that exceed the limit are rejected with a clear error message before calling DNR APIs.

# 19. Final verdict

Rev14 is the corrected 10/10 plan for a real current-Chrome MV3 blocker.

It removes fantasy features and overbuilt modules, keeps the strongest parts of the architecture, uses the larger Chrome 121+ safe dynamic-rule capacity correctly, gives users a powerful local rules workspace, and preserves store compliance by forbidding automatic rule fetching and remote executable logic.

The new engineering standard is:

```text
not minimal
not speculative
not file-only
not remote-updated
buildable in current Chrome MV3
superior only where the certificate proves it
```



Additional Rev14 corrections:

- Production attribution uses `rulesMatchedInfo[]` from `getMatchedRules()`, not a nonexistent `rulesMatched` array.
- Production attribution does not search by `requestId`, because `MatchedRuleInfo` does not expose request IDs. It filters by `tabId` and `minTimeStamp`, then resolves `rule.rulesetId` and `rule.ruleId` through the source map.
- Exact request details are explicitly debug-build-only through `onRuleMatchedDebug`; packed release UX must describe attribution as recent tab-level matched-rule evidence.
- Static capacity is split into guaranteed and opportunistic profiles. Only the guaranteed profile may support public superiority claims; opportunistic extra capacity is runtime-only.
- The stale globally-unique-static-ID wording is removed. Numeric rule IDs must be unique within a ruleset; cross-ruleset diagnostics use `rulesetId:ruleId`.
- Static ruleset validation is a release blocker because invalid static rules in packed extensions may be ignored by Chrome rather than surfaced as developer-visible errors.


# 19. Rev14 final verification gates

A release is 10/10 only if all of the following machine-checkable gates pass:

- `getMatchedRules()` code compiles against the real API shape: `RulesMatchedDetails.rulesMatchedInfo[]`, `MatchedRuleInfo.rule.ruleId`, `MatchedRuleInfo.rule.rulesetId`, `tabId`, and `timeStamp`.
- No production code expects `requestId` from `getMatchedRules()`.
- `onRuleMatchedDebug` is excluded from packed-release logic and allowed only in unpacked development builds.
- Static rule IDs are unique within each ruleset; source-map keys are globally unique as `rulesetId:ruleId`.

- Opportunistic static profile activates only after runtime `getAvailableStaticRuleCount()` checks.
- Safe dynamic user rules are capped at Chrome’s dynamic-rule limit and unsafe dynamic/session rules remain under their separate unsafe caps.
- Regex rules pass `isRegexSupported()` where available and fail if they exceed the estimated 2 KB compiled-size limit.
- The certificate records browser version, DNR capability profile, static profile mode, unsupported syntax, and attribution mode.
