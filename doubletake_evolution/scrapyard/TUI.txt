You are operating inside the DoubleTake repository.

# MISSION

Transform DoubleTake from its current desktop React UI into a real full-screen terminal application built with OpenTUI React.

The target experience is:

```
doubletake
```

which launches an interactive terminal UI comparable in interaction quality to OpenCode, Codex CLI, Claude Code, or Microsoft's `edit` application:

* full-screen terminal UI
* keyboard-first operation
* mouse support
* focusable controls
* resizable panes
* scrolling
* menus/dialogs where useful
* command input
* streaming activity/output
* clear status/navigation
* responsive terminal resizing

Linux and Windows are primary TUI targets.

Do not require native OpenTUI execution on iOS.

Preserve or adapt the existing web React frontend as a thin browser/mobile/iOS client where useful.

The OpenTUI and web clients must operate against the same DoubleTake core. They must not contain independent implementations of DoubleTake behavior.

# AUTHORITY

The current checked-out DoubleTake repository is authoritative.

The current `main` branch is authoritative unless repository policy explicitly states otherwise.

Never assume something exists because it was previously discussed.

Before every change:

```
inspect the actual code
```

Never design from memory when the repository can answer the question.

# NON-NEGOTIABLE INVARIANTS

Throughout the migration:

1. Preserve existing DoubleTake capabilities unless removal is explicitly required by the completed target architecture.

2. Do not duplicate business logic in the TUI.

3. Keep UI concerns separate from:

   * orchestration
   * agents
   * models/providers
   * governance
   * persistence
   * Git operations
   * watchdog/recovery
   * task execution
   * evidence
   * runtime state

4. Prefer existing services and abstractions when they are sound.

5. Refactor only when necessary to create a clean reusable boundary.

6. Never perform a large rewrite when an incremental migration can accomplish the same result.

7. Every iteration must leave the repository in a valid state.

8. Every completed iteration must have observable evidence.

9. Never remove the old implementation before its required replacement works.

10. Never call placeholder, mocked, stubbed, TODO, visually simulated, or unreachable functionality complete.

# MIGRATION PRINCIPLE

Do not "rewrite the React UI."

Instead:

```
separate reusable DoubleTake behavior from presentation
↓
expose clean UI-facing state/actions/events
↓
build equivalent OpenTUI interaction
↓
verify parity
↓
retire obsolete desktop-web presentation code
```

Existing React concepts such as state models, hooks, schemas, commands, event handling, validation, and shared logic may be reused when appropriate.

DOM-specific components, CSS, browser-only behavior, and browser APIs must not be mechanically transplanted into OpenTUI.

# 6. OPEN TUI RULES

Use OpenTUI React as the desktop terminal presentation layer.

Do not replace the requirement with:

* Electron
* Tauri
* xterm.js
* browser-rendered terminal simulation
* ncurses-style ad hoc rendering when OpenTUI already provides the needed primitive
* a plain CLI pretending to be the requested TUI

Use OpenTUI-native interaction patterns wherever practical.

The terminal interface must progressively support:

* keyboard navigation
* mouse interaction
* predictable focus
* scrolling
* text input
* selection where useful
* resize handling
* long-running asynchronous activity
* live/streaming updates
* non-blocking rendering
* status feedback
* errors
* cancellation where DoubleTake supports cancellation
* clean shutdown

Do not tie core behavior to terminal rendering lifecycle.

# 7. CORE/UI BOUNDARY

Any capability required by more than one interface should live below the presentation layer.

Preferred direction:

```
UI ACTION
    ↓
DoubleTake application/service interface
    ↓
DoubleTake core capability
    ↓
state/event/result
    ↓
UI renders result
```

Avoid:

```
OpenTUI component
    ↓
directly reimplements runtime/Git/model/agent logic
```

and avoid:

```
Web React implementation
    ↓
OpenTUI imports browser component internals
```

Share behavior, types, schemas, commands, state models, and interfaces where justified.

Do not force visual component reuse between browser React and terminal React when it creates coupling.

* Git operations
* network operations

* model startup

Do not invent state names if an authoritative state model already exists.

# 9. TERMINAL SAFETY

Ensure terminal state is restored after:

* normal exit
* Ctrl+C / supported interrupt
* handled errors
* failed startup
* task failure

Avoid leaving:

* alternate screen state stuck
* cursor hidden
* mouse capture enabled
* malformed terminal modes
* raw mode enabled

Use framework-supported lifecycle mechanisms when available.

# BLOCKED-STATE RULE

If implementation is genuinely blocked:

1. prove the blocker from repository/runtime evidence
2. determine whether the blocker can be removed locally
3. make the smallest safe change that removes it
4. continue the migration

Do not respond to an ordinary engineering obstacle by stopping and asking what to do.

Do not invent external dependencies when an internal solution exists.

If an external/environmental dependency truly prevents verification, implement everything safely possible and record the exact unresolved verification boundary.
