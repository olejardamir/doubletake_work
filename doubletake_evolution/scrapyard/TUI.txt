## Target and scope
Proposed `doubletake` full-screen OpenTUI React terminal client on Linux/Windows, with keyboard/mouse/focus/scroll/resize/streaming, clean shutdown, live agent/task/model/provider/Git/log/recovery state, workspace and command input. Proposed CLI: `doubletake`, `doubletake .`, `doubletake <workspace>`, `run`, `status`, `logs`, `serve`. Existing browser React remains a thin mobile/iOS and remote client; native OpenTUI on iOS is explicitly out of scope. Electron/Tauri/xterm.js/browser terminal simulation do not satisfy this specific proposed target.

## Architectural invariants
- UI clients consume a shared, explicitly defined application/service state/action/event interface backed by existing DT core. Never duplicate governance, agents, models, persistence, Git, watchdog, evidence or task execution in presentation components. Reuse behavior/types/schemas, not DOM/CSS components.
- Preserve existing features until verified functional parity or an explicit obsolete classification. Avoid large speculative rewrites, independent backend implementations and simultaneous permanent desktop implementations.
- Terminal renderer must remain responsive during asynchronous work; represent authoritative task states, not invented state labels. Restore cursor/raw mode/alternate screen/mouse capture after normal exit, interrupts, startup failures and handled errors.
- Platform-specific adapters may handle Windows/Linux path, spawn, signal, executable discovery and packaging differences. Distinguish implemented/static/CI/runtime verification; do not claim unexecuted Windows checks.

## Bounded verification contract
Before any proposed change, independently inspect current DT code, UI capabilities, entrypoints, interfaces, packaging and tests. Track per-capability existing web behavior, core source of truth, TUI equivalent, verified status and retirement decision; categories may be UNMAPPED, CORE-COUPLED, INTERFACE-READY, TUI-PARTIAL, TUI-COMPLETE, VERIFIED, OBSOLETE. Select one architectural or functional blocker, then a small complete slice with explicit acceptance, regression risks and evidence. Historical suggested first proof: real `doubletake` launches OpenTUI, renders live authoritative status, resizes and exits with terminal restored; no mock-only completion.

For each slice check startup, type/build/lint, unit/integration, command input, async streaming, keyboard/mouse/focus/resize, cancellation/reconnect where supported, Linux/Windows packaging, persistence/governance and browser/mobile regression. Capture exact code revision, tests actually run, failures, remaining gaps; compile-only or simulated UI does not prove runtime parity. After proven replacement, retire obsolete desktop-only code and adapters without removing required web/mobile functionality. Final independent audit must check real launch, feature parity, shared core, interaction, reliability, no placeholders, platform scope and cleanup.
