## Primary provenance and what was actually checked

1. **Rundgren, Jordan, Erdtman, RFC 8785, June 2020, JSON Canonicalization Scheme (JCS)** — https://www.rfc-editor.org/rfc/rfc8785.html (directly read §§1, 3.1–3.2, Appendix B and Appendix E). This **Informational**, non-standards-track RFC defines hashable canonical JSON using I-JSON, deterministic object-key ordering, ECMAScript-compatible number/string serialization and UTF-8. It preserves Unicode strings *as-is* rather than normalizing them; rejects duplicate keys, lone surrogates and unsupported numbers. Its Appendix B gives adversarial numeric serialization vectors (including -0 → 0), and Appendix E demonstrates how native subtype conversion can silently change strings.
2. **Bray, RFC 7493, March 2015, I-JSON** — https://www.rfc-editor.org/rfc/rfc7493.html (directly read §§2–3). I-JSON excludes duplicate object member names, mandates UTF-8 and warns that numbers exceeding binary64 precision may be interpreted inconsistently.
3. **Eisenhofer et al., _Cross-Language Differential Testing of JSON Parsers_, 2024** — https://casa.rub.de/en/research/publications/detail/cross-language-differential-testing-of-json-parsers (independent curiosity/frontier track; **research-group abstract only**, not full paper or reproduction). Authors report discrepancies across 22 parsers, including keys, numbers and strings. This is a warning to test *actual parser behavior*, not evidence of any DT vulnerability.
4. **Original test-data pointer** — https://github.com/cyberphone/json-canonicalization (listed by RFC 8785 Appendix I; repository contents and license NOT audited in this run; link only, no source/code redistribution).

**Source facts vs inference:** JCS can produce deterministic bytes for *eligible JSON under its exact rules*. It does NOT establish that DT historical records use JSON, JCS, compatible writer versions, a trustworthy version field or the same hash input. It cannot authenticate a forged record, repair a broken historical signature, or authorize alternate acceptance. A JCS digest computed today is NOT comparable to an old stored digest unless the original authenticated writer contract explicitly used those same canonical bytes. Independent authenticity/provenance remains a separate gate.

**Synthetic controls (owner-authorized isolated test only):** Freeze input bytes, declared writer version, authentic source of the writer contract, expected digest and evaluator revision. For each *authenticated* supported writer version, test: (P1) exact original representation; (P2) key-order/whitespace variant that is genuinely valid *under that historical writer's declared digest contract*; (N1) changed value/leaf; (N2) forged or cross-version writer tag; (N3) duplicate decoded keys; (N4) unpaired Unicode surrogate / Unicode normalization alteration; (N5) float/large-integer and -0 corner cases; (N6) untrusted record with correct-looking recomputed JCS digest. Use RFC Appendix B as external **test-oracle inspiration**, not as an alternative source of historical authority. Keep original and shadow-computed bytes separately; no writeback.

**Discriminator:** Compare (A) current verifier against (B) *read-only, independently specified* per-version canonicalization diagnostic. Record accepted/rejected/indeterminate for each case, mismatched byte offset, digest input contract, interpreter/runtime versions, false accepts, false rejects, runtime and source provenance. A valid P2 exists only if the *original authenticated historical contract* makes it valid; do not assume mere semantic JSON equivalence is valid for a byte-hash chain.

**Pass/fail:** A meaningful new diagnostic is reproducible separation of a *proven legitimate* version representation from N1–N6, with **zero tampered/unauthenticated acceptance, zero state mutations, no side effects**, and improvement over A on held-out records. If A already distinguishes them, `ALREADY_PRESENT`. If no authenticated writer contract, `INDETERMINATE`; if B accepts N1–N6, `UNSAFE_REJECT`.
