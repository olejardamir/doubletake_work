## Atomic negative mechanism and limitations

**Observed source branch, not observed runtime failure:** `RollbackRecovery.recover` uses `target_step.memory_snapshot` if available. When `None`, it warns that partial recovery may lose data, then calls `context.memory.clear()`, restores only `target_step.action_outputs`, and truncates history. `Memory.clear` clears working memory/change history. `ExecutionStep.memory_snapshot` is optional, BUT ordinary `RunContext.add_step` normally populates it automatically. **Normal-path reachability, third-party benchmark reproducibility and DT applicability are UNKNOWN.** Distinct from IS-022's downstream-committed-consumer semantic veto: this is a missing-snapshot *partial-reconstruction* hazard even without a dependent consumer.

**Disposable falsifier (proposed, not executed):** Create synthetic memory `{authorization:'deny', provenance:'sha-A'}`, a target step with `memory_snapshot=None` and `action_outputs={answer:'ok'}`; predict unrelated keys are lost. Controls: complete snapshot restores all keys; no prior step refuses; committed external effect cannot be undone by memory restore. Also test partial/malformed and wrong-run snapshots, concurrency and preservation of immutable sentinels. Never use live retained history.
