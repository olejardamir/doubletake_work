## Precise observed negative mechanism (third-party code only)

The public `RollbackRecovery.recover` in `runtime/recovery.py` uses a full `memory_snapshot` when present. **If that field is None**, the alternative branch logs a warning explicitly acknowledging possible data loss, then calls `context.memory.clear()` and restores **only** `target_step.action_outputs`; it then truncates execution history. `Memory.clear()` empties working memory and its change history. `RunContext.ExecutionStep.memory_snapshot` is an optional field; `RunContext.add_step` normally supplies a snapshot if none is passed. Therefore the unsafe branch is statically present but **its reachability during normal operation is unverified**.

**Concrete falsifiable counterexample:** construct an entirely disposable synthetic context with two independent keys, `authorization='deny'` and `provenance='sha-A'`, and a target step with `memory_snapshot=None` and `action_outputs={'answer':'ok'}`. After the rollback branch, static reading predicts the two independent keys are absent. A second case with a complete snapshot should restore them. A third with no prior step must refuse. A fourth with a committed downstream effect must not claim that in-memory restoration undoes the effect. These are **proposed tests**, not observed execution results. Do not infer that the paper's proposed semantic-recoverability gate uses this fallback or that the current DT implementation has it.

**Why distinct from IS-022:** IS-022 asks whether rollback invalidates **already-committed downstream consumers**. This entry isolates **destructive partial reconstruction when the required snapshot is missing**, even without another consumer, and supplies an actual source-level negative branch plus an attribution correction. It is also distinct from IS-001 retained-history disposition and IS-020 clean-environment test reproduction. A GitHub code-search nonmatch is not proof of DT absence.
