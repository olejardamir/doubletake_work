## Primary-source mechanism and boundaries
- The paper separates **requirements imposed by tasks** from **behavior exhibited by the current skill**. It constructs a fixed capability set and a task×capability incidence matrix from task specifications *before* observing execution outcomes. The capability labels must represent reusable procedures, not merely topic similarity.
- After a round, it computes each capability's support fraction and observed success on training tasks that require it; their product with remaining failure mass prioritizes the most widely unresolved requirement. Evidence for a revision is selected by the same capability. A candidate is retained only if paired whole-skill validation improves on both a separate selection set and the training set; an untouched final test set measures transfer.
- Author-reported four-benchmark held-out accuracy: 70.7% unweighted mean versus 63.3% for SkillOpt, with a 5.7-point mean advantage over each benchmark's best competing method; reported average evolution-token use 24% below the closest iterative baseline. Randomizing task–capability assignments reduced final accuracy by as much as 20.2 points. **These are authors' results, not independent reproduction or DT performance.**
- Assumptions/negative evidence: recurring requirements must be extractable in advance and editable by shared skill guidance; fixed mappings may become stale when tasks or authority contracts change. Editing one shared skill can regress unrelated tasks; whole-skill tests are therefore essential. The study is bounded to one optimizer–target configuration, not proven across indefinite autonomous runs, changing domains, or DT. The source is a preprint; independent replication and reusable implementation licensing were not established.

Include ambiguous/nonrecurring requirements and changed-contract negatives. Record annotation disagreements, all task scores, revision choices, token/time cost and regressions. 2. **Falsifiable capability delta:** At identical execution/evaluation budget, the requirement-guided approach must improve held-out *verified task success* over both controls, with no increased unauthorized effects or unrelated-task regressions, and demonstrably different useful revision/evidence choices. Reject as NO_DELTA if equal or worse, ALREADY_PRESENT if current DT passes, or NOT_APPLICABLE if tasks lack stable shared requirements.
