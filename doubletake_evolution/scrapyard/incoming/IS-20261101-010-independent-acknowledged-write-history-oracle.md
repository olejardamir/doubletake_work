## Distinct mechanism and why it may matter

The Director's public mission reports an isolated **acknowledged-update loss counterexample** in two-owner snapshot persistence, including sequential long-lived/short-lived-owner operations, and asks for a genuine no-loss owner contract with negative/restart tests. The existing tests already *characterize* the unsafe behavior; this is **not** a proposal to repeat them or to add another writer.

A possible distinct contribution is an **independent, source-agnostic oracle** for recorded histories: given an owner-approved abstract state-machine contract, record call, return/acknowledgement, final durable read and restart boundary; have a checker independently decide whether an allowed sequential history could explain those observations. This can falsify a purported fix even when its own unit tests are green, and produce a small reproducible witness. It would supplement—not replace—existing DT tests and authority controls.

**Crucial applicability gate:** linearizability is a *strong* guarantee. DT may promise only no loss of acknowledged additions after quiescence/restart, not immediate linearizable reads. In that case use the weaker explicit accepted-set preservation invariant in a standalone oracle; do **not** claim Porcupine failure proves a DT defect under an unpromised stronger contract. The actual owner contract and current test parity are **unverified** from this Scout.

## Falsifiable permission-safe experiment (proposal only)

- **Prerequisite / authority:** Existing state owner confirms the operation and acknowledgement semantics, durable read timing, and whether a synthetic isolated fixture is already authorized. No production history, protected B1 record, live state or private source is copied into the public repo. No new runtime access or software installation assumed.
- **OUTWARD:** Freeze a tiny self-authored public-safe operation trace with distinct synthetic IDs `a` and `b`. Define abstract `accept_add(id)` as successful only when the specified contract says the addition is durably acknowledged; define `reject_add(id)` as a non-acknowledgement; define `read_after_quiescence_and_restart()` as the final observable set. If the contract demands linearizability, model operations as a single logical object in Porcupine. If not, evaluate the narrower no-loss invariant offline. Preserve exact operation/ack identity and partial ordering, not fabricated timestamps.
- **INWARD (only if approved):** Compare this independent oracle to the already existing 3.5.2 isolated lost-update fixture and any approved corrected implementation. Do not change DT persistence, ownership, approval logic, retained records, or the Director's mission.
- **GROUND positive:** Sequential successful acknowledgements `a`, then `b`, and a post-restart final set `{a,b}` must pass. Under concurrent accepted additions, any allowed order must still preserve both after the contract's durability boundary.
- **GROUND negative:** Both `a` and `b` acknowledged, but final persisted set `{b}` must fail the no-loss oracle; a valid digest on `{b}` must not mask the lost acknowledgement. A refused `a` before acknowledgement with final `{b}` is a *passing refusal*, not lost acknowledged data. Include replayed `a`, interrupted/crash-before-ack, delayed reads and deliberately wrong operation-order metadata as controls; report inconclusive rather than force a verdict if an acknowledgement or observation is missing.
- **Benchmark/parity:** Compare the oracle's pass/fail classification against existing source-level no-loss tests on the *same* fixtures. Accept candidate value only if (i) it detects the known lost-ack counterexample, (ii) accepts legal refusal and preserved-history controls, (iii) adds an independent reproducible witness or catches a new fault without false positives, and (iv) bounded execution cost is measured. A tool installed, a prompt amended, or a checker passing a toy trace alone is **not** verified DT Ground.
- **Reproduction constraints:** Pin checker revision and fixture SHA, document contract and timing model, preserve raw public-safe call/return traces, cap concurrency and history length, and repeat in fresh processes. For partitioning, prove independence first; DT shared snapshot likely precludes naive key-by-key partitioning. Validate any reported anomaly manually.
