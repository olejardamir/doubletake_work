## Primary sources directly examined

1. **RFC 9110, HTTP Semantics** (IETF, June 2022), sections **13.1.1** and **13.2**: https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1 and https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2 . An origin server uses **strong** entity-tag comparison for `If-Match`; a failed precondition normally prevents the method and yields 412. **Subtle exception:** a server may respond 2xx when it can determine the requested change was *already applied*. The RFC explicitly warns that this exception can be risky for non-cooperating clients using shared state as a semaphore/non-atomic increment. This is a standard's allowance, **not** a guarantee that a particular DT writer implements HTTP or this exception.
2. **RFC 5789, PATCH Method for HTTP** (IETF, March 2010), section **2**: https://www.rfc-editor.org/rfc/rfc5789.html . An HTTP PATCH must apply its changes atomically (or none). For base-dependent patches the RFC recommends conditional requests with a strong ETag. HTTP PATCH atomicity is not a substitute for crash-durable acknowledgement or correct owner-defined concurrency semantics.
3. **RFC 6902, JSON Patch** (IETF, April 2013), sections **4.6** and **5**: https://www.rfc-editor.org/rfc/rfc6902.html . `test` checks a specified JSON value; failed operations prevent a successful whole-document HTTP PATCH. `add` to an existing object member can replace it, so an unguarded patch is **not automatically a no-loss merge**. A `test` is safe as a concurrency guard only when the **entire test-and-update is atomic** at the actual storage owner.

## Precise mechanism / non-obvious risk

**Conditional update** and **acknowledged durable addition** are different predicates. A strong ETag / version CAS can prevent a stale full-snapshot overwrite, but a generic HTTP success code can still be ambiguous: RFC 9110 allows an already-applied response on an `If-Match` mismatch. Therefore, a consumer cannot automatically infer **new durable contribution by this operation ID** from 2xx alone. Conversely, an honest stale-write refusal (e.g. 412) is not a lost *acknowledged* write. Repeated identical payloads from distinct writers also must not be silently conflated without an owner-defined identity/idempotency rule.

**DT relevance (inference):** The Director reports B4 acknowledged-update loss in an isolated two-owner snapshot case, and unresolved canonical writer/acknowledgement authority. This standards-derived distinction could sharpen **3.5.2**'s eventual writer contract and **IS-010**'s independent oracle: classify NEW_ACK, IDEMPOTENT_ALREADY_APPLIED, REJECTED_STALE and INCONCLUSIVE distinctly before asserting no-loss. It may also prevent the analogous mistake in **7.8.1** of counting a reused same-revision success/receipt as a new local mission execution. The latter analogy is not a proposal to change 7.8.1 or to substitute HTTP status for a real process observation.

**Novelty gate:** IS-005 concerns invariant-confluent vs coordinated transitions; IS-010 concerns an independent consistency oracle; IS-008 concerns read-only canonicalization. This candidate's narrow possible delta is **the standards-permitted success/acknowledgement ambiguity plus an atomic stale-write precondition control**, not a new database, generic CAS literature, a rehash of known lost-write tests, or authorization to modify B1 history. If current DT already distinguishes these cases, mark ALREADY_PRESENT / do not promote.

- **OUTWARD:** In a disposable self-authored model, two synthetic writers A/B read revision 0 and propose distinct additions `a` and `b`. Freeze operation IDs, read revision, precondition, response classification, final read and restart observation. Compare an unconditional snapshot baseline against an **atomic** version/ETag precondition; if HTTP is not the actual owner, translate the *invariant* to its documented CAS contract rather than adding HTTP.
- **INWARD (Director/owner approval required):** Only if current authorized test-owner parity is insufficient, evaluate the same frozen cases with the existing canonical writer and independent oracle; do not add another state owner or weaken existing fail-closed protection. A JSON Patch `test`+update sequence is merely one possible scratch representation; it is not a production prescription.
- **GROUND positive:** A's revision-0 update is genuinely accepted, B's stale revision-0 update is **rejected without acknowledgement**, B re-reads revision 1 and its separately authorized retry is accepted; after the specified durable restart boundary both `a` and `b` remain. Classify the first B attempt REJECTED_STALE, not LOST_ACK.
- **GROUND negative:** Unconditional B replacement after A's acknowledgement leaves only `b` and must FAIL the no-loss invariant. An implementation that evaluates a `test` and writes separately (race between them) must FAIL. A weak ETag or ambiguous validator must not be treated as a strong conditional guard. A `test` failure must not partially apply earlier patch operations.
- **Acknowledgement ambiguity controls:** Replayed *same operation ID* whose effect is already present may be `IDEMPOTENT_ALREADY_APPLIED` but must not count as a fresh contribution; a *different operation ID* with identical payload cannot inherit that acknowledgement without an owner-defined equivalence proof. Missing response, delayed ack, process crash before ack, and final read before the agreed durability boundary are INCONCLUSIVE, not success.

Accept value only if it (i) avoids false new-ack classification for at least one valid already-applied case, (ii) rejects a stale overwrite and a non-atomic test/update, (iii) retains legal refusals and no-loss positive controls, and (iv) demonstrates a previously absent discriminator at bounded cost. ## Limitations, permissions and counterevidence

- RFC 9110 governs HTTP origin servers; private DT's shared-state writer may not be HTTP and may already implement correct CAS/idempotency. No indexed code-search hit is **not** evidence of absence. Private current writer and owner contract remain **unverified**.
- Strong `If-Match` avoids one class of stale replacement; it does **not** by itself provide crash durability, multi-resource transactions, fair retries, no-loss storage or authorization. HTTP `If-Match: *` tests existence, not revision equality. RFC 9110's 2xx exception is permitted only when the server can establish prior application; arbitrary 2xx cannot be assumed to mean that.
