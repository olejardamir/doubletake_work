## Distinct reusable mechanism (source fact vs proposed transfer)

**Source fact:** CaMeL separates a trusted control plan from untrusted retrieved content, then tracks the **origin/dependencies of values** (including derived values and, in strict mode, conditional control dependencies) and enforces tool-specific data-flow policy at the actual action boundary. Simply quarantining untrusted text is insufficient: it can still poison an otherwise authorized tool argument, e.g. recipient, filename or destination. The paper identifies policy-authoring burden, user-approval fatigue, side channels, utility loss and missing atomic rollback for partial side effects. Its security guarantees are threat-model- and policy-dependent, not universal.

**Proposed DT hypothesis (UNVERIFIED):** At an already authorized governed external discovery→knowledge→assimilation seam, a source-derived summary/parameter may lose its original untrusted provenance before being used as a tool argument or a cross-agent recommendation. If that precise gap exists, **propagating origin and permitted-use labels through transformations to the existing authorization decision** could prevent source text from silently becoming action authority. This is *not* a request for a second controller, a new model, a new permission layer, or any change to protected history.

**Novelty comparison:** Public planning already discusses governed intake, provenance, authorization, replay and untrusted-source boundaries; an existing private E17/other policy mechanism may already handle derived-value provenance. No indexed `CaMeL` match was found in the accessible public inventory/offload, but search absence is **not** implementation absence. Before any Director promotion, inspect actual existing policy/taint/argument-binding tests and mark `ALREADY_PRESENT` if covered. This source adds a *specific derived-argument information-flow falsifier*, not a generic prompt-injection recommendation.
