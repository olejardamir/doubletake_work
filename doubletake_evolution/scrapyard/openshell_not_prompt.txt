# OpenShell as an optional DoubleTake enforcement substrate — historical proposal

**Original blob:** `3015885a7b72feb88035a2fa4e91500b0718ae04`. Source was an unapproved integration recommendation, **not** a DT implementation plan or proof. Public primary references: https://github.com/NVIDIA/OpenShell ; https://docs.nvidia.com/openshell/latest/how-it-works/policies/overview ; https://docs.nvidia.com/openshell/latest/how-it-works/policies/prover . Docs reviewed 2026-11-01. Exact upstream version, license of reused components, DT parity, owner, installation and host authority UNKNOWN; no code imported.

**Potential mechanism:** preserve DT's existing Sandbox interface, policy/authorization, evidence ledger, promotion/rollback and LocalSandbox for explicitly trusted work. An optional OpenShell backend could enforce DT-derived filesystem read/write roots, process identity, network host/port/binary and supported REST method/path rules for untrusted generated/external code. DT remains sole policy authority; OpenShell is enforcement only, not a second governance engine. Candidate lifecycle: authorize → compile least-privilege policy → compare candidate against DT-defined maximum → create isolated sandbox → execute → record deny/allow evidence → destroy and verify cleanup. Include sandbox/version, DT and compiled-policy digests, effective policy, prover coverage/result, identity, denied actions, provider bindings, exit and cleanup in existing evidence owner.

**Primary-source caveat:** NVIDIA's policy prover checks only modeled properties, and reports `unsupported` for unmodeled combinations (including some GraphQL/MCP, wildcard/path and symlink cases). A `within_boundary` result is **not** proof the policy is sufficient for a task or enforced by a running sandbox; require runtime negative tests and actual effective-policy capture. Static filesystem/process settings differ from dynamic network updates; provider attachments may expand effective network permissions. No automatic fallback from required high-assurance OpenShell to unrestricted LocalSandbox on error.

**Negative controls / benchmark:** Compare an already authorized disposable DT sandbox baseline against OpenShell on filesystem/symlink escape, forbidden process, network/DNS exfiltration, unauthorized REST POST/DELETE, metadata-service access, credential leakage, child policy escalation, provider-added rules, unsupported prover features, policy-widening and missing backend. Require denials before effects, no authority expansion, honest unsupported outcomes, deterministic teardown, restart/rollback and bounded cost. Compare on the *same* workload and verify no false blocks. Child policy must remain within parent's proven maximum only for covered domains. Do not claim the model is complete or the actual DT code has a missing sandbox boundary.

**Research gate:** First identify current DT canonical sandbox owner, already available enforcement and authorized fixture. Only if a distinct missing property is reproduced and the owner approves may an optional adapter be proposed to Director. Do not install, route Borg work, grant network/credentials, alter host policy or modify private DT from this scrapyard note.
