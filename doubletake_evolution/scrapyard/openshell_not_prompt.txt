Yes. For DoubleTake, I would make the OpenShell work exactly this:
1. Add OpenShell as a new DoubleTake sandbox backend. Keep DT's existing Sandbox interface and LocalSandbox; implement something like OpenShellSandbox for high-assurance execution. OpenShell supports isolated sandboxes with filesystem, process, network, and provider policies. GitHub
2. Do not port OpenShell's low-level sandbox implementation. Do not copy its Landlock, supervisor, proxy, gateway, container drivers, syscall controls, or Rust security internals. Use upstream OpenShell as the execution substrate so NVIDIA's implementation can continue receiving security fixes.
3. Create a DoubleTake → OpenShell policy compiler. Translate DT's existing SandboxPolicy, DataScope, operation permissions, protected paths, and execution contracts into OpenShell YAML: DT read roots → filesystem_policy read-only; write roots → read-write; DT network permissions → endpoint rules; allowed processes/tools → binary/process permissions. OpenShell is deny-by-default for access not granted by policy. NVIDIA Docs
4. Make DoubleTake remain the policy authority. DT decides what the agent may do; OpenShell merely enforces that decision. Do not create a second independent governance system that can bypass DT's L0/L1/evidence/gate architecture.
5. Run Borg-adopted and externally assimilated code through OpenShell. Especially external repositories, generated code, newly created tools, experimental skills, autonomous coding workers, and unknown third-party components.
6. Run self-evolution experiments through OpenShell where feasible. Candidate patches/tests should execute inside an isolated OpenShell workspace before DoubleTake considers promotion.
7. Integrate OpenShell's policy prover into DT promotion gates. Before executing or broadening authority, prove that the proposed OpenShell policy remains inside a DoubleTake-defined maximum boundary. OpenShell's prover specifically supports checking whether one policy exceeds an allowed boundary. NVIDIA Docs
8. Use hierarchical policy boundaries for Borg workers. A child/sub-agent must never receive greater filesystem/network/provider authority than its parent. DT generates the child policy; OpenShell prover verifies child ≤ parent/max-boundary.
9. Move secrets toward OpenShell provider bindings. Do not expose raw GitHub/model/API credentials to autonomous agents when avoidable. OpenShell can associate credentials with approved endpoints/provider profiles and enforce the associated network/binary rules. GitHub
10. Upgrade DoubleTake's network controls from boolean/host-level policy to fine-grained enforcement. Compile permissions for destination + port + calling binary and, where applicable, HTTP method/path. For example, permit GitHub GET while denying an unauthorized POST or DELETE; OpenShell demonstrates this exact type of L7 enforcement. GitHub
11. Feed OpenShell events back into DT's evidence system. Record sandbox ID, OpenShell version, DT policy digest, generated OpenShell-policy digest, prover result, execution identity, denied filesystem/network/process actions, provider bindings, exit status, and policy changes.
12. Bind OpenShell evidence to DT promotion/rollback. A candidate should not be promoted merely because tests pass; DT should also prove that it ran under the expected sandbox/policy and that no forbidden authority was used.
13. Fail closed. If OpenShell is requested but unavailable, policy compilation fails, the prover fails, or the requested sandbox cannot enforce the required boundary, DT must not silently fall back to unrestricted LocalSandbox.
14. Keep LocalSandbox for development/tests and explicitly trusted operations. Current DT LocalSandbox uses local subprocess execution; it should not be mistaken for the same security level as OpenShell.
15. Add capability detection/configuration. DT should detect whether OpenShell is installed/reachable and expose something like sandbox_backend = local | openshell, with high-risk Borg/self-evolution flows able to require openshell.
16. Add lifecycle management. DT should be able to create → configure → execute → collect evidence → destroy an OpenShell sandbox, with deterministic cleanup after failed runs.
17. Add adversarial tests. At minimum test: filesystem escape, symlink escape, shell escalation, forbidden binary, DNS/network exfiltration, unauthorized HTTP methods, credential theft, metadata-service access, policy widening, child-agent privilege escalation, and fallback bypass.
18. Add comparative proof tests against current DT enforcement. Demonstrate that something DT's static policy layer says is forbidden is actually prevented at runtime inside OpenShell.
19. Add OpenShell to DoubleTake's evidence/proof pipeline. Create a dedicated proof package—something analogous to prove-openshell-integration—covering backend availability, policy translation, boundary proving, execution containment, credential handling, denial evidence, and cleanup.
20. Do not replace DT's existing governance components. Keep DT's policy registry, AdapterEnforcer, evidence ledger, promotion/rollback, Borg, capability fabric, assimilation, memory, routing, FICs, and L0/L1/L2 architecture. OpenShell sits underneath them as the strong runtime enforcement layer.
21. Pin a supported OpenShell version and test upgrades. OpenShell is actively evolving, so DT should declare a compatible version range and run policy/integration regression tests before upgrading. Current OpenShell 0.1.x has expanded isolation primitives and APIs. GitHub
22. Only after this integration is proven, route the high-risk Borg/self-improvement paths through it by default. That is the final acceptance point.
In short, the implementation target is:
DoubleTake decides → OpenShell enforces → DoubleTake verifies and records the evidence.
That is what I would implement before returning to the scientific-paper sequence.
