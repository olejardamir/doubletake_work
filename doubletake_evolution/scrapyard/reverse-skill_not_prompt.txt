## Three candidate mechanisms
1. **Live tool-readiness index**: distinguish capability advertised → binary installed → executable path/version known → MCP/service registered → service healthy → permitted executable *now*. Upstream `skills/scripts/refresh-tool-index.sh` and PowerShell equivalent refresh a snapshot; stale snapshot must fail safely, not imply live availability. DT's existing sealed Python adoption is not proof of universal host/MCP readiness.
2. **Declarative environment bootstrap**: upstream `bootstrap-manifest.json` proposes version-pinned acquisition via package managers, Git, binary releases, services, MCP and manual steps. Any DT use requires explicit owner permission, supply-chain integrity, platform compatibility, bounded cost, verification, rollback and **no implicit installation**. Hypothesized locus: existing Skill2Env/adoption/capability fabric; current implementation parity UNKNOWN.
3. **Route ↔ benchmark coverage invariant**: upstream `routing-benchmark.json`, `skills/config/routing.json` and `verify-routing-coherence.ps1` connect routing configuration to regression coverage. A DT-compatible *proposal* is to test every routable capability with (a) canonical request, (b) request lacking capability name, (c) paraphrase, (d) multi-capability positive, (e) near-neighbour negative, (f) unrelated negative. Integrate into existing SkillGym **only if** current evaluator lacks equivalent checks; do not create another controller/test stack.

## Other donor elements and constraints
Compact precedent index (`field-journal/_index.md`), route/config/document consistency and scope/case workflow are mostly overlapping with existing DT knowledge/governance; security-specific workflows should not become universal DT defaults. Upstream current README describes client-neutral routing and Windows/Ubuntu CI; source content and benchmark counts evolve and are not current DT metrics. Historical claims of `52/52` SkillGym and earlier capability-participation failure are **unverified for current DT HEAD**.

## Falsifiable small test / decision
Owner first identifies current canonical routing/SkillGym and tool-readiness paths. On frozen authorized isolated fixtures, compare baseline against a proposed coverage check: no-name positive and near-neighbour negative must expose an otherwise missed routing defect without increasing false positives; stale/uninstalled/version-mismatch/MCP-unhealthy cases must not be marked executable. Reject as ALREADY_PRESENT if existing DT tests already cover these; reject as NO_DELTA if no independently observed improvement. No actual installation or DT code edit authorized. Revisit on a verified routing or tool-readiness failure, not just this donor's existence.
