## Distinct conditional objective
If an **existing** authorized DT HTTP capability/retrieval/tool-result consumer uses a response cache, distinguish **(A)** RFC 9111 storage, selection, shared-cache reuse and freshness/validation rules from **(B)** the application's independent current principal, tenant, tool-context and permission checks. RFC 9111 §3.5 restricts shared-cache reuse of Authorization-bearing requests unless explicit enabling response directives and their requirements permit it. Matching URI alone is insufficient: method and Vary-selected request headers matter; `Vary: *` never matches; stale responses require applicable allowance or successful validation. Even RFC-compliant cache reuse is not authorization to disclose another principal's data. A public/shared-cache directive does not override application isolation. Conversely, do not forbid legitimately shareable responses for independently authorized consumers. Distinguish HTTP response freshness from freshness of external facts.

- **P2:** Explicitly shareable response, matching variant and independently authorized second consumer: allow lawful sharing, without blanket denial.
- **N1:** Two principals request same URI with distinct confidential results: never disclose first principal's response to second on URI-only match.
- **N2:** Authorization-bearing request without applicable shared-cache-enabling directive: deny shared reuse.
- **N3:** Changed Vary-selected request header or `Vary: *`: no incorrect variant match or reuse.
- **N4:** Stale response lacking applicable stale permission or successful validation: no reuse.
- **N5:** Permission revoked after insertion: cached content cannot bypass current application authorization.
