## Conditional objective, owner and interfaces
**Only if** an owner-authorized existing DT HTTP evidence/tool contract actually verifies RFC 9421 HTTP Message Signatures, require a separately approved *application signature profile* specifying: mandatory covered HTTP components and signature parameters, accepted signature algorithms, authorized key discovery and identity binding, key/algorithm/context suitability, component derivation context (including request/response and proxy-derived target URI where applicable), verification errors, replay-window/nonce policy, and independent action/evidence authorization. Bind verification to the *actual* method, target, authority, selected content integrity policy and signer identity relevant to the specific consumer. A valid cryptographic signature covering too few fields does not authenticate uncovered method/target/content. HTTP Message Signatures do **not directly sign the body**: when body integrity is required, the owner-approved profile must require coverage of a suitable verified digest field and verify that digest against the actual body. Signed timestamps/nonces alone do not guarantee replay prevention. Valid signature is NEVER permission to invoke a tool, trust a claim beyond signed scope, retrieve remote keys automatically, or override a denied operation.

**Potential owners/consumers are hypotheses:** an existing HTTP evidence-ingest verifier or tool-response/request contract, its security-policy owner and authorized key resolver. Do not create a parallel signer, remote key retrieval authority, new service or expanded permissions. HTTP headers, key identifiers, signature parameters, proxies and external content are untrusted until independently verified under approved policy. Separate cryptographic VALID, coverage COMPLETE, signer AUTHORIZED, replay ACCEPTABLE, digest MATCHED and tool action PERMITTED outcomes; otherwise fail closed or return policy-defined UNKNOWN.
