## Distinct value beyond DT-IP-0011
DT-IP-0011 proposes an independent oracle for **loss of acknowledged writes**. This narrower companion discriminates **what an acknowledgement means** when a conditional request fails, is retried, or has already taken effect. A successful HTTP response can denote an already-applied equivalent operation rather than a *new* accepted contribution; a stale refusal is legal and not a lost acknowledgement. Distinguish `NEW_ACK`, `IDEMPOTENT_ALREADY_APPLIED`, `REJECTED_STALE`, `INCONCLUSIVE`, `LOST_ACK` only under an owner-authenticated operation identity, acceptance, response and durability contract. Do not double count repeated operation IDs or conflate identical payloads from distinct IDs without proof of equivalence. A response alone cannot prove durable or unique contribution.

**Protocol-conditional rules:** HTTP `If-Match` strong ETag matching; `If-Match: *` proves existence rather than revision equality; weak validators cannot substitute for strong comparison. RFC 9110 permits a 2xx response where a failed condition corresponds to an already-applied state change, with cautions for non-cooperating writers. HTTP PATCH requires all-or-none application; RFC 6902 JSON Patch `test` compares typed values and `add` replaces an existing object member. Failed `test` must not leave preceding patch steps applied. A detached read/test followed by a separate write is not atomic. CAS can prevent stale overwrite but **does not itself prove** durability, authorization, fairness, multi-resource atomicity or stronger consistency. If current DT storage is not HTTP, translate only the justified invariant; do not force HTTP semantics onto file/database writers.
