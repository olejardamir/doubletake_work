## Conditional testable behavior
1. Preserve the historical sequence as *data-flow hypothesis*: system goal → whole-system pseudocode → bounded unit pseudocode → enforceable per-unit contract → validate whole bundle → freeze approved contract revision → bounded coding handoff → actual implementation → independent tests/trace/rollback/review. Separate intent from verified runtime behavior.
2. A bounded unit contract includes stable ID and source-unit reference, one responsibility and explicit exclusions, inputs/outputs, public interface, state owner, pre/postconditions, invariants, permitted/forbidden dependencies, effect/idempotence class, failure/retry, test oracle, observability, exact edit boundary, rollback and residual risks. Shared types are defined once with fields/enums/defaults/serialization/version/compatibility. Never infer missing owner or permission.
3. Construct a **unit dependency DAG** with explicit provided/consumed interfaces and single state ownership. Check both directions: every source unit has one matching contract; every contract names a source unit; every required behavior has an owner; every dependency and interface resolves; no duplicate type/state owner, hidden cycle or unapproved interface change. Explicitly approved architectural cycles require separate review, never silent acceptance. Do not create new durable views where existing DT records suffice.
4. Reject missing source/contract, vague or untestable oracle, undefined or forbidden dependency, duplicate owner/type, unauthorized cycle, stateful unit without rollback, incompatible shared-type version and stale revision with precise cause. Historical candidate statuses `READY_FOR_IMPLEMENTATION`, `BLOCKED_MISSING_CONTEXT`, `BLOCKED_CONFLICTING_DOCUMENTS`, `BLOCKED_UNDEFINED_INTERFACE`, `BLOCKED_UNTESTABLE_CONTRACT`, `BLOCKED_UNSAFE_DEPENDENCY`, `BLOCKED_DUPLICATED_OWNERSHIP` are compatibility examples, not a mandate for new state machine. Readiness is not permission.
5. When a real authorized consumer exists, build an immutable **per-unit revision-bound handoff** using existing packet machinery: contract ID/revision, source pseudocode digest, minimal relevant excerpt, exact allowed paths, shared types, dependency/side-effect rules, authority and accepted write scope, positive/negative tests, validation commands, resource budget, terminal states, rollback and evidence schema. Do not send all project context by default; retries must preserve obligations, never degrade to one-line prompt. Existing tool-effect policy independently authorizes each effect.
6. A contract correction requires a narrow owner-approved delta naming affected unit, dependents, rationale and changed interface; stop affected implementation until reconciliation. A coder may not silently edit frozen contract to rationalize accidental code. Implementation order follows real DAG, not an imposed rewrite of existing modules.
7. Evidence trace must connect source unit ↔ approved contract ↔ actual files ↔ real consumer ↔ tests/results ↔ completion. Per-unit evidence identifies inspected/changed revisions, executed commands and outcomes, deviations, negative controls, effect authority, rollback and independent reviewer. Distinguish `IMPLEMENTED`, `NO_CHANGE`, `PARTIAL`, `BLOCKED`, `REJECTED` and reviewer `ACCEPTED`/`REJECTED_NEEDS_FIX`/`REJECTED_SCOPE_DRIFT`/`REJECTED_TEST_INSUFFICIENT`/`REJECTED_TRACEABILITY_GAP`/`REJECTED_SECURITY_RISK` only when backed by observed evidence. A populated matrix or commit alone is not proof of consumer behavior.
