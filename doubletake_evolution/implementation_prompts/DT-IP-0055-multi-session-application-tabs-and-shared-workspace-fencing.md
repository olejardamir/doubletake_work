## Conditional behavior and interfaces
1. **Application tabs (source §§3,5–8,17,25–26).** Distinguish browser window/tab from in-app session tab; canonical `session_id` and `run_id`. Multiple independent sessions can be opened, created, switched, renamed and closed within one browser page. Closing a view never implicitly cancels a run, loop or subagent. Session-keyed drafts, messages, attachments, scroll, pending questions, unread/status and async callback ownership; global state only where truly shared. Accessible keyboard navigation, focus, overflow and status; safe `sessionStorage` page-local layout, not authoritative chat/run data; legacy migration and missing-session restore.
2. **Run admission and lifecycle (§§9–10,18–20,32,38.5–38.12).** Atomic, idempotent request fingerprint and admission binding session, run, owner, immutable configuration, governance, loop/subagent and resources. Same-session conflicts deterministic; cross-session concurrency real. No process-global “current session/run”. Exact-run cancel, pause/resume and question/permission reply with ownership/authorization checks, stale fencing, cooperative safe points and terminal compare-and-set. `cancelling` is not terminal `cancelled`; do not infer termination from acknowledgment. No generic global-stop fallback; Stop All is separately permissioned and explicit. Cancellation must stop/verify owned child process trees, not kill by name.
3. **Event and replay correctness (§§11–13,18,24,32,38.2–38.4,38.25,38.28).** Server-enforced tenant/session/run-scoped WebSocket authorization; versioned event envelope and per-run ordered durable sequence, no unscoped global queue. Atomic sequence+event append or recoverable gap protocol, dedupe, retention floor, gap detection, bounded subscriber queues, slow-client isolation, snapshot/replay reconciliation and terminal durability. Event may precede HTTP start response: correlate by durable client request identity; no loss, phantom run or duplicate send. Backend crash/restart distinguishes recoverable admitted work, terminal work and interrupted work; never pretend an in-memory run resumed.
4. **Browser ambiguous outcomes (§§8,12,24,32,38.6–38.7).** Durable/reconcilable browser-side request identity/outbox for create/start, canonical fingerprint, retry after timeout/refresh/restart without duplicate run. Async completions always target captured session/run, never whichever tab is currently selected. Same session in two browser windows must reconcile.
5. **Shared live workspace (§§3.8,14–16,24,32,38.13–38.16,38.26–38.27).** Sessions share the SAME repository/workspace, not per-session clones/worktrees. Canonical real paths (including symlink/case/alias), expected file revisions and atomic same-file conflict detection; bounded multi-file mutation preflight and rollback/partial-failure evidence. Fresh-read, snapshot-sensitive validation and structural workspace generation (checkout/branch/revert may invalidate evidence even when file hashes match). Coordinate direct AND indirect writers with hierarchical broad-writer barriers across actual supported process topology. Do not impose one whole-run mutex. External unfenceable mutation-capable subprocesses require proven death before lock release or workspace quarantine. Ports, caches, temp files and other named resources have exact ownership.
6. **Persistence, deletion and governance (§§17–23,26,32,38.17–38.23,38.29).** Concurrent-safe session/transcript updates (no whole-object last-write-wins), immutable attachment/artifact ownership, bounded fair global capacity and overload responses, exact permission/question/subagent/loop isolation, authorization independent of guessable session IDs. Session deletion is an explicit state machine respecting active runs and delete/start races. Structured stale/conflict responses and redacted observability. Self-hosted code changes and backend auto-reload are explicit global lifecycle boundaries.
7. **Compatibility and rollout (§§25–26,29–31,33–37).** Stage backend identity/ownership before UI activation; migrate legacy single-session caches and endpoints safely, preserve existing single-session behavior. Owner-approved changes only, explicit fallback/rollback and no silent legacy global cancel. Document actual deployment topology and supported browser/storage model.
